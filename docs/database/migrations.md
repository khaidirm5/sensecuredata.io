# Database Migrations

## Overview

Database schema changes for Sentinel Secure Data Intelligence Platform are managed with Alembic.

Alembic keeps database changes versioned so the schema can be updated consistently across development and other environments.

The migration configuration is located in:

```text
backend/alembic.ini
```

Migration files are stored in:

```text
backend/alembic/versions/
```

---

## Migration Structure

The Alembic directory currently contains:

```text
backend/alembic/
├── README
├── env.py
├── script.py.mako
└── versions/
```

`env.py` contains the Alembic environment configuration, while the `versions` directory contains individual schema changes.

---

## Creating a Migration

When a database model is changed, a new Alembic migration should be created to represent the schema change.

For an automatically generated migration:

```bash
cd backend
alembic revision --autogenerate -m "describe the change"
```

The generated migration should be reviewed before applying it to the database.

Autogenerated migrations should not be treated as automatically correct. Changes to constraints, indexes, relationships, and data transformations should be checked manually.

---

## Applying Migrations

To apply all pending migrations:

```bash
cd backend
alembic upgrade head
```

This updates the database to the latest migration.

---

## Checking Migration Status

The current migration state can be checked with:

```bash
cd backend
alembic current
```

To see the available migration history:

```bash
cd backend
alembic history
```

---

## Rolling Back a Migration

A migration can be moved back by one revision with:

```bash
cd backend
alembic downgrade -1
```

Downgrades should be used carefully, especially when the migration has already been applied to a database containing important data.

## Index Changes

Database indexes are also managed through Alembic.

For example, the project contains migrations for sales dashboard composite indexes:

```text
2435fafd8795_add_sales_dashboard_composite_indexes.py
```

There are also migrations that remove redundant indexes from existing tables.

This keeps index changes version-controlled instead of applying them manually to the database.

---

## Development Workflow

A typical database change follows this process:

```text
Modify SQLAlchemy Model
        ↓
Create Alembic Migration
        ↓
Review Migration
        ↓
Apply Migration
        ↓
Test Application
```

The migration file should be committed together with the model changes that require it.

---

## Migration Safety

Before applying a migration to a shared or production database:

- Review the generated SQL operations.
- Check whether existing data is affected.
- Check changes to foreign keys and constraints.
- Check index creation and removal.
- Test the migration against a development database first.

Destructive schema changes should be handled carefully because they may permanently remove existing data.
